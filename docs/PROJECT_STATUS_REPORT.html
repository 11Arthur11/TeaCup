گزارش مستقل برای مطالعه و تصمیم‌گیری؛ این فایل بخشی از رابط کاربری اصلی پروژه نیست.

مشکلات و Gapهای فعلی

۱. قرارداد ناقص DTO محصولات عمومی

مسیرهای محصولات عمومی و ادمین در OpenAPI بیشتر با Example مستند شده‌اند و schema خروجی صریح ندارند. در نتیجه generator نوع پاسخ را unknown تولید می‌کند و فرانت‌اند مجبور به parse محافظه‌کارانه است.

۲. ناسازگاری schema ثبت محصول

بدنه POST /v1/admin/products/add هنوز به AbstractNewResourceRequest اشاره می‌کند، در حالی که Example فیلدهای محصول، قیمت، دوره و Presentation را می‌فرستد.

۳. فیلدهای نوع‌محور Resource Detail

فیلدهایی مانند آدرس، پورت، وضعیت TeaSpeak و Privilege در برخی نسخه‌های OpenAPI حذف می‌شوند، ولی UI به آن‌ها نیاز دارد. مدل بهتر است با discriminator و DTO مستقل برای TeaSpeak و AudioBot تعریف شود.

۴. مجوز عملیات ادمین روی endpointهای کاربر

شروع، توقف، ویرایش AudioBot، Privilege و Playlist از همان endpointهای سرویس کاربر اجرا می‌شوند. backend باید دسترسی ROLE_ADMIN را برای مدیریت سرویس هر مالک به‌صورت صریح تضمین کند.

۵. Presentation به‌صورت JSON داخل String

این مدل انعطاف‌پذیر است، اما اعتبارسنجی backend روی ساختار داخلی ندارد. JSON خراب در فرانت‌اند نادیده گرفته می‌شود و ممکن است محتوای محصول ناقص نمایش داده شود.

۶. Polling گسترده

بخش‌های زنده هر پنج ثانیه به‌روزرسانی می‌شوند. حفظ scroll و state تا حد زیادی انجام شده، اما افزایش تعداد کاربران می‌تواند تعداد درخواست‌ها را بالا ببرد.

مشکلات UI و فاصله‌ها

  • بعضی صفحه‌های مدیریتی اطلاعات زیادی را در یک فایل و یک renderer بزرگ نگه می‌دارند؛ نگهداری و تست آن دشوارتر شده است.
  • کارت‌های جدول‌محور در موبایل به اسکرول افقی وابسته‌اند و باید با داده واقعی طولانی دوباره بررسی شوند.
  • دیالوگ‌های پیچیده محصول و Playlist به تست Keyboard Navigation و Focus Trap نیاز دارند.
  • Landing به API عمومی وابسته است؛ برای خطای موقت، Empty/Error State وجود دارد اما Skeleton پیشرفته و retry خودکار محدود است.
  • فاصله بین بعضی کارت‌های Detail از کلاس‌های عمومی تبعیت می‌کند و بهتر است یک سیستم spacing ثابت برای صفحه‌های Detail تعریف شود.

تغییرات پیشنهادی

اولویت بالا

تعریف schema واقعی برای Product List/Detail/Create و Resource Detailهای نوع‌محور.

اولویت متوسط

تقسیم فایل‌های بزرگ صفحه ادمین به feature module و افزودن تست integration برای عملیات اصلی.

اولویت تکمیلی

استفاده از SSE/WebSocket برای رویدادهای زنده و کاهش polling در صفحه‌های پرترافیک.

  • افزودن DTOهای PublicProductResponse، AdminProductListResponse و AdminProductDetailResponse.
  • تبدیل features و badges به آرایه JSON واقعی در نسخه بعدی قرارداد، در صورت امکان.
  • افزودن capabilities به Resource Detail تا فرانت‌اند فقط عملیات مجاز همان سرویس را نمایش دهد.
  • افزودن تست Playwright برای Login، خرید محصول، پرداخت، تیکت، Resource Detail و عملیات ادمین.
  • افزودن ETag یا Cache-Control برای دسته‌ها، محصولات عمومی و فایل قوانین.
  • ثبت نسخه قرارداد فرانت Presentation و migration برای تغییرات آینده.

معیار آماده‌بودن نسخه انتشار

  • تمام endpointهای اصلی روی محیط staging با نقش‌های User، Support و Admin آزمایش شوند.
  • مسیر پرداخت موفق و ناموفق با درگاه واقعی کنترل شود.
  • عملیات حذف و تمدید اجباری سرویس دارای Audit Log سمت سرور باشد.
  • محصولات عمومی، دسته‌های خالی و Presentation خراب با داده واقعی تست شوند.
  • بررسی موبایل در عرض‌های 360، 390، 768 و دسکتاپ 1440 پیکسل انجام شود.

نتیجه فعلی: پروژه از نظر ساخت و TypeScript پایدار است، اما پیش از انتشار عمومی به تثبیت schemaهای OpenAPI و تست مرورگری مسیرهای بحرانی نیاز دارد.

این گزارش با هدف خوانایی و چاپ ساخته شده و هیچ وابستگی به CSS یا JavaScript پروژه TeaCloud ندارد.
